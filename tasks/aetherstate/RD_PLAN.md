# AetherState Human-Style R&D Plan

Goal: transform the OpenEvolve loop from a pure optimizer into a scientific-research assistant that generates hypotheses, runs controlled experiments, keeps a research notebook, and uses past findings to guide future work.

---

## Phase 1: Explicit Hypotheses and a Research Notebook

1.1 **Add a `HYPOTHESIS` field to the bundle**
   - Extend `aetherstate_bundle.py` with a top-level string: `RESEARCH_NOTEBOOK`.
   - Before each mutation, the LLM must append a short note: hypothesis, expected effect, and rationale.

1.2 **Prompt the LLM to think like a scientist**
   - Update `tasks/aetherstate/config.yaml` so the system message requires:
     - A hypothesis statement before any SEARCH/REPLACE block.
     - A prediction of which metrics will change and why.
     - A note on what would falsify the hypothesis.

1.3 **Store notes per program**
   - When a program is added to the OpenEvolve database, its research-note entry is stored in `Program.metadata["research_note"]`.
   - The note is passed to future LLM prompts as part of the evolution history.

**Deliverable:** Each evolved program carries an auditable research note.

---

## Phase 2: Controlled Experiments and Ablation Studies

2.1 **Parent re-evaluation under the same seed**
   - When a child is evaluated, also re-evaluate its parent with the *same* random seed and self-play data size.
   - Store `delta_metrics = child_metrics - parent_metrics`.
   - This isolates the effect of the mutation from run-to-run variance.

2.2 **Ablation mode**
   - Add an evaluator mode that strips out the latest mutation and re-runs, so the LLM can see whether a change actually mattered.
   - Useful when a child stacks multiple changes.

2.3 **Statistical confidence**
   - Run the micro-training gate 2-3 times per candidate with different seeds.
   - Report mean and std-dev of win_rate and speed.
   - Reject changes whose improvement is not statistically significant.

**Deliverable:** The loop measures the *causal effect* of a mutation, not just a raw score.

---

## Phase 3: Mechanistic and Diagnostic Metrics

3.1 **Add a diagnostic suite to the C++ engine**
   - `tactics_test`: evaluate the engine on a small set of known tactical puzzles.
   - `material_balance`: report average material difference when winning.
   - `draw_rate`, `average_game_length`, `blunder_rate`.

3.2 **Expose diagnostics as OpenEvolve metrics**
   - `tactics_accuracy`, `draw_rate`, `blunder_rate`, `avg_game_length`.
   - Use these as extra MAP-Elites axes so behavioral diversity is preserved.

3.3 **Compare to a fixed baseline**
   - Run a short match against a known engine or a hand-built baseline after every mutation.
   - Report Elo difference with confidence intervals.

**Deliverable:** The loop understands *how* a program plays, not just whether it wins.

---

## Phase 4: Research Agendas and Meta-Analysis

4.1 **Periodic meta-analysis iteration**
   - Every N iterations, pause mutations and ask the LLM to review the experiment log.
   - The LLM produces a short `RESEARCH_AGENDA`: which directions look promising, which are dead ends.

4.2 **Agenda-driven mutation**
   - The agenda is injected into the system message for the next block of iterations.
   - This prevents the loop from thrashing between unrelated ideas.

4.3 **Dead-end tracking**
   - If a class of mutations consistently fails, the LLM records it in the research notebook.
   - Future prompts avoid those directions unless new evidence appears.

**Deliverable:** The loop plans its own research strategy instead of blindly mutating.

---

## Phase 5: Literature Review and Ancestor Analysis

5.1 **Rich ancestor context in prompts**
   - When proposing a mutation, the LLM is shown:
     - The parent program's code.
     - The parent's research note.
     - A summary of what worked and failed in the recent past.

5.2 **Cumulative findings document**
   - Maintain `tasks/aetherstate/FINDINGS.md` (auto-generated by the LLM every checkpoint).
   - Contains: best architectures, best training tricks, open questions.

5.3 **External knowledge injection**
   - Optional: allow the user to seed `FINDINGS.md` with known chess-engine research (e.g., NNUE, transformer policies) so the LLM can build on it.

**Deliverable:** The loop builds institutional memory, not just a bag of programs.

---

## Phase 6: Long-Horizon Validation for Promising Candidates

6.1 **Two-tier evaluation**
   - **Tier 1** (cheap): compile, short self-play, speed, win-rate vs random.
   - **Tier 2** (expensive): longer training, match against trained anchor, tactical suite.
   - Only candidates that pass Tier 1 with high confidence get Tier 2.

6.2 **Reserve a validation pool**
   - Top candidates from each island are periodically sent to Tier 2.
   - Results feed back into the research notebook and agenda.

6.3 **Final-run candidate selection**
   - The program chosen for the expensive final training run is the one with the best Tier 2 score, not necessarily the best Tier 1 score.

**Deliverable:** The final expensive run uses a candidate validated on real evidence, not just a cheap proxy.

---

## Phase 7: Reproducibility and Experiment Tracking

7.1 **Traceable artifacts**
   - Every program stores: full code, architecture, training command, seed, metrics, and research note.
   - OpenEvolve's existing `evolution_trace` can be enabled for this.

7.2 **Re-run script**
   - Add `tasks/aetherstate/reproduce.py <program_id>` that re-evaluates a saved program exactly.
   - Critical for verifying surprising results.

7.3 **Checkpointed research notebook**
   - The research notebook is saved at every checkpoint alongside the database.
   - Resume restores the notebook state.

**Deliverable:** Every result is reproducible and attributable to a specific experiment.

---

## Implementation Order

1. Phase 1 + 2 (hypotheses + controlled ablations) — lowest cost, highest scientific value.
2. Phase 3 (diagnostic metrics) — improves the quality of the fitness signal.
3. Phase 4 + 5 (agendas + findings memory) — moves from optimization to directed research.
4. Phase 6 (long-horizon validation) — essential before the expensive final run.
5. Phase 7 (reproducibility) — should be done in parallel with the above.

---

## Risks and Mitigations

| Risk | Mitigation |
|------|------------|
| Hypothesis notes use up prompt budget | Keep them short (1 paragraph) and summarize older notes |
| Controlled experiments double evaluation cost | Run ablations only for top candidates or every 5th iteration |
| Diagnostic metrics are noisy | Report confidence intervals; do not use as primary fitness |
| LLM ignores agenda | Include agenda in system message and ask LLM to address it |
| Long-horizon validation is expensive | Only run on programs in the top 10% of Tier 1 scores |
